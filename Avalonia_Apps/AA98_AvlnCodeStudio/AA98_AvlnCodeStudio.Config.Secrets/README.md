# Config.Secrets

`AA98_AvlnCodeStudio.Config.Secrets` defines UI-neutral contracts for selecting and using credential backends independently of ordinary configuration stores.

`CredentialId` contains only stable service/name/scope identifiers. `ICredentialProvider` exposes availability, retrieval, storage, and deletion without coupling consumers to a platform or a vault format. A retrieved `CredentialSecret` is owned by the caller and must be disposed. A secret passed to `SetAsync` is borrowed for that call only; providers must not retain the instance.

`CredentialSecret` keeps its own mutable character buffer and clears it on disposal. This does not erase caller-owned buffers, immutable strings created by integrations, copies made by providers, OS caches, swap, or crash dumps. Callers should avoid converting secrets to strings and should keep their lifetime short. `ToString()` is always redacted.

`CredentialProviderCatalog` resolves only an explicitly requested provider ID, rejects duplicate IDs, and never selects a fallback. Hosts should surface unavailable/locked status to the user rather than switching backends implicitly. Fake-provider contract tests cover ownership-compatible set/get/delete and explicit provider selection.

The Workbench AI Chat keeps only the Plan, Build, or Debug agent choice and conversation controls. Plan and Debug expose read-only workspace tools; Build can additionally request build/test operations, which still require explicit user approval. Debug mode currently provides guidance and workspace inspection, but does not control the debugger session. Credential management is available separately from the View menu. The selected credential manager is a user setting and is filtered to the current platform; an unsupported saved value is visibly marked and can be replaced with a supported option rather than silently changed. `None` is available for session-only keys, and no provider is selected by default.

The Workbench user settings select a provider preset and may override its endpoint/model. Built-in system templates provide OpenAI, local Ollama, and IFM connection metadata; deployments may override the template list in the system configuration. Enable `UseAIProviderProfiles` to use separate endpoint/model overrides for OpenAI, Ollama, IFM and one Custom provider; empty values use the selected preset's template, while Custom needs an endpoint. This is opt-in: existing global `AIEndpoint` and `AIModelId` values remain unchanged and apply again when profiles are disabled. Configured profile endpoints are validated before saving, including inactive profiles. Additional named profiles are not yet supported. Templates and profile settings contain no secrets; do not put credentials in endpoint URLs or model identifiers. The API key remains session-only unless explicitly saved, and startup never auto-loads a credential. Loading a saved key makes it available to the current in-memory AI client; deleting the stored entry also clears the current session key. Changing the endpoint clears the session key and starts a fresh conversation context; earlier messages remain visible but are not forwarded to the new endpoint. An in-flight credential load is discarded if its endpoint, provider or session key changes. Each stored AI key is scoped to the normalized HTTP(S) endpoint using an opaque SHA-256 identifier, not the profile name; profiles sharing an endpoint share that credential scope. Older unscoped entries are not automatically loaded or migrated; remove them explicitly from the OS credential store if they are no longer needed.

The settings dialog normally displays the active connection's fields; changing the provider setting edits the dialog draft and becomes active only on Apply. The separate `Inspect profile` selector shows an individual provider's fields without changing the selected provider or enabling profiles. Its `ActiveConnection` choice restores normal display; `Show all provider fields` overrides the filter temporarily. Template and copy actions target the active connection and are disabled during individual profile inspection, so they cannot unexpectedly edit another profile. The preview and credential dialog always refer to the active connection, not the inspected profile. An overview lists all invalid configured profile endpoints without displaying their values. Each error has an `Inspect <provider> profile` action to show that profile and scroll its endpoint into view; an editable endpoint receives keyboard focus. Read-only endpoints are shown without transferring focus. `Show invalid profile fields` displays all fields. Display-only choices do not bypass read-only restrictions or make the draft dirty; actual edits still require Apply and are discarded on Cancel. `Copy global endpoint` and `Copy global model` explicitly copy the corresponding legacy value into an empty editable active profile field without removing the original or overwriting a profile value.

`WindowsCredentialProvider` stores generic credentials for the current Windows user using the Windows Credential Manager APIs. Credential IDs are mapped to a stable opaque target name; secret bytes are UTF-8 encoded, the caller-owned input is not retained, and the managed/native temporary buffers are cleared where owned. Generic credential blobs are limited to 2560 bytes. The provider reports unavailable on non-Windows platforms and does not prompt or claim to determine whether the user profile/keyring is unlocked. Its real write/read/delete smoke test is opt-in via `AVLN_RUN_CREDENTIAL_MANAGER_SMOKE=1` and always attempts to delete its unique temporary entry.

`LinuxSecretServiceProvider` uses the default Secret Service collection through `Ace4896.DBus.Services.Secrets` 1.6.0 and requests a DH-encrypted D-Bus session. It stores only a SHA-256-derived opaque credential ID as the lookup attribute and uses a generic item label. It checks collection/item lock state before operations and reports a locked collection without explicitly requesting an unlock. The underlying client may prompt if the keyring changes state between that check and the operation. The upstream binding currently exposes neither connection disposal nor cancellation for in-flight D-Bus calls; one connection is retained per provider instance, and cancellation is honored while waiting for the provider and before backend operations start. A missing bus/service, failed D-Bus connection, or missing default collection is reported as unavailable by status; data operations continue to surface their errors. A real Secret Service round-trip is opt-in via `AVLN_RUN_SECRET_SERVICE_SMOKE=1` on Linux. An injectable backend seam keeps credential hashing, UTF-8 conversion, buffer cleanup, locked-state propagation and CRUD behavior covered without a running D-Bus/keyring; the real OS path remains a separate opt-in check.

There is not yet an encrypted local vault. No secret may be copied into `Config.Service` JSON files. A provider must report unavailability explicitly; consumers must not silently fall back to plaintext storage or another backend.
